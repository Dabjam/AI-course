# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использован датасет `S12-hw-dataset.csv`, прогнозировалось следующее значение колонки `target` (one-step ahead).
- Разбиение сделано по времени: `train / validation / test = 70% / 15% / 15%` без перемешивания.
- Сравнились подходы `B1` (naive-last), `B2` (moving-average), `B3` (Ridge на лаговых признаках), `R1` (GRU).
- Лучшим по `validation MAE` оказался `R1 (GRU)`.

## 3. Данные и постановка задачи

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: `target`
- Частота временного ряда: 1 час
- Горизонт прогноза: 1 шаг вперед
- Размер датасета: `4320`
- Диапазон дат: `2025-01-01 00:00:00` - `2025-06-29 23:00:00`
- Есть ли дополнительные внешние признаки: нет (использовались производные признаки из `target` и `date`)
- Комментарий: в ряде заметна выраженная внутридневная сезонность, есть колебания уровня и локальные пики/просадки. Пропусков нет, поэтому отдельная импутация не требовалась. Из-за сезонности и шума задача плохо решается совсем простыми baseline, но хорошо подходит для лаговых признаков и RNN.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: хронологически, первые 70% в train, следующие 15% в validation, последние 15% в test.
- Какие доли или интервалы использовались: `3024 / 648 / 648` наблюдений.
- Почему `random split` здесь некорректен: при случайном перемешивании модель получает информацию из будущего в train, поэтому метрики на validation/test становятся смещенно оптимистичными.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: `lag_1`, `lag_7`, `lag_14`
- Какие rolling-признаки использовались: `rolling_mean_7`, `rolling_std_7` (через `shift(1)` для исключения утечки)
- Какие календарные признаки использовались: `day_of_week` (`dow`) и `hour`
- Как обрабатывались пропуски после построения лагов/rolling: удаление первых строк с `NaN`, где лаги/роллинги еще не определены
- Использовалось ли масштабирование и где именно оно обучалось: для `B3` применен `StandardScaler` только по train-признакам; для `R1` - `StandardScaler` по train-target

## 5. Модели и эксперименты (B1, B2, B3, R1)

Опишите коротко и сопоставимо:

- B1 (`naive-last`): прогноз равен последнему известному значению (`lag_1`)
- B2 (`moving-average`): прогноз равен сдвинутому скользящему среднему (`window=24`)
- B3 (`ridge-lag-features`): `Ridge(alpha=1.0)` на лаговых, rolling и календарных признаках
- R1 (`gru-forecast`): однослойная `GRU(hidden_size=64)` на оконном представлении ряда

Дополнительно:

- Основная метрика выбора лучшей модели: `MAE` на validation
- Дополнительные метрики: `RMSE`, `MAPE`
- `window_size` для `GRU`: `24`
- Batch size: `64`
- Максимальное число эпох: `20`
- Optimizer: `Adam`
- Learning rate: `1e-3`
- Как сохранялась лучшая модель: по минимальному `val_MAE` сохранялся `state_dict` в `./artifacts/best_gru.pt`

## 7. Анализ

Наивный baseline `B1` получился не самым слабым, что ожидаемо для ряда с сильной краткосрочной зависимостью между соседними наблюдениями.  
`Moving average` с окном 24 (`B2`) показал худшие метрики: сглаживание оказалось слишком инерционным и хуже подстраивалось под резкие колебания.  
`Ridge` на лаговых и календарных признаках (`B3`) улучшила качество относительно `B1`, потому что модель использует сразу несколько масштабов памяти (короткие и более длинные лаги).  
`GRU` (`R1`) дала лучший результат, так как последовательная модель лучше учитывает структуру временного контекста внутри окна.  
По графикам видно, что ряд имеет выраженную сезонную компоненту (внутрисуточные паттерны), поэтому календарные признаки и оконный подход действительно полезны.  
Потенциальные утечки в такой задаче чаще всего возникают из-за `random split`, а также при некорректном построении rolling/lag без `shift`.  
В работе эти риски закрыты: split строго по времени, а rolling-признаки сдвинуты на один шаг назад.  
Выбор модели по validation, а не по test, принципиален, потому что test должен оставаться честной финальной проверкой обобщающей способности.  
Самые заметные ошибки модели появляются на участках с резкими локальными изменениями уровня ряда.

## 8. Итоговый вывод

Для этой задачи в качестве базового подхода я бы выбрал `R1 (GRU)`, так как она показала лучшую `val_MAE` и стабильный результат на test.  
Если нужен быстрый и интерпретируемый старт, то `B3 (Ridge + лаговые признаки)` - хороший простой baseline, который уже дает разумное качество.  
Переход к `GRU` имеет смысл, когда ряд содержит выраженную временную структуру и нелинейные зависимости, которые линейной модели сложнее уловить.  
Главный практический вывод: для временных рядов корректный `temporal split` и контроль утечек важнее, чем выбор “сложной” модели сам по себе.
